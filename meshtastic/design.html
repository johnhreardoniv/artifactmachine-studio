LESSON 01 / REQUIREMENTS

Name the service first.

A mesh design begins with people, places, and the messages they need to exchange.

Describe one real use

Write a sentence such as: “Two people should exchange short messages between the trailhead and the campground while the solar node stays at the ridge.” Mark the endpoints and the places between them. Use the reliable, mixed, and failed areas from Course 2. Identify who carries a node, who has a phone or computer connected to it, and who can check the fixed site.

Define success before changing hardware: for example, both people can exchange a numbered message and reply at three named stops on repeated visits. Define the operating window, whether location sharing is wanted, and what happens if a message fails. Meshtastic uses a low-bandwidth shared radio channel; it is a supplementary messaging path, so a critical plan needs an independent fallback.

Design brief · one page
  • People, endpoints, and the route between them
  • Message type: public channel, private channel, or direct message
  • Measured pass, mixed, and failed areas
  • Success test and fallback if it fails

The next lessons answer a sequence of design questions: Where? What role? Who can read it? Does it need the Internet? Who maintains it?

LESSON 02 / COVERAGE DESIGN

Choose sites on purpose.

A good site connects the places your users care about and can stay powered, accessible, and permitted.

Compare candidates

Plot the current P1 Pro location and one or two candidate locations on the Meshtastic Site Planner. Enter realistic antenna heights, receiver assumptions, band, and power for your region. Run each prediction separately. Then overlay the real field observations from Course 2. A terrain model cannot promise delivery through every building or tree, so favor sites that can be tested.

Assess each candidate beyond radio reach: sunlight, weather exposure, mounting permission, physical security, access for inspection, and whether a public position broadcast would reveal a private address. A site that appears ideal on a map but cannot be maintained is a fragile design.

LESSON 03 / RADIO CAPACITY

Spend airtime carefully.

More forwarding is not always better. Every repeated packet occupies the same shared radio channel.

Start with normal clients

Meshtastic’s current role guidance recommends CLIENT for most nodes. Clients send, receive, and intelligently rebroadcast. CLIENT_MUTE can suit a personal node sitting beside a stronger node on a busy mesh because it does not repeat. CLIENT_BASE can favor a well-placed personal base node. ROUTER and REPEATER are specialized: using them casually can increase collisions and consume useful hops.

For your three-device plan, keep all as CLIENT unless your field data gives a specific reason to change one. Document the reason, expected improvement, and a before-and-after test. Coordinate infrastructure-role changes with a local mesh community if your node can affect other users.

Count automatic traffic too

Messages are only part of the load. Position updates, telemetry, neighbor reports, range tests, and optional MQTT downlinks can all add packets. Meshtastic device telemetry exposes channel utilization and airtime. Check those values before adding recurring reports. Keep range-test transmissions temporary and use reporting intervals that match an actual need.

Traffic budget

List each planned message or automatic report, who needs it, and how often. Remove any report whose value is unclear. Write down your starting role for each node and why.

LESSON 04 / TRUST

Decide who can read it.

Radio reach and message privacy are separate design decisions.

Separate public and private traffic

Meshtastic’s default primary channel key is published. Treat messages sent with that key as readable by others who share the radio settings. If a group needs privacy, create a channel with a fresh private key and share it only with intended members. Keep a secure record of who holds that key and how to replace it if it is disclosed. Do not publish channel QR codes or keys in screenshots, logs, or course assignments.

Channel settings distinguish message groups; the LoRa modem preset and frequency slot govern the radio link. A private channel does not give each group a separate band or unlimited airtime. Meshtastic encrypts channel payloads but leaves packet headers visible for routing. Someone who records traffic and later obtains the channel key may be able to read earlier messages. An unattended solar relay does not need your private channel key to forward traffic; avoid putting that key on it unless the site must read or send private messages. Review the current encryption documentation before using the mesh for sensitive material.

Decide what location to share

A fixed solar node and portable GPS trackers may report position. Check position precision and broadcast behavior on each device and channel before deployment. A public position from a fixed node can reveal the site. If the use case does not need location, do not broadcast it just because the hardware has GPS.

Trust plan

For each channel, write its purpose, intended members, whether location is shared, and who manages the key. Leave the key itself out of the document. Add a process for replacing a lost or exposed key.

LESSON 05 / OPTIONAL EXTENSIONS

Bridge only for a reason.

The local LoRa mesh works without the Internet. A gateway solves a different reach problem.

Decide whether a bridge helps

Meshtastic’s MQTT module can forward packets through an Internet connection between meshes. That can help people beyond radio range, but it introduces Internet dependence, configuration, privacy decisions, and possible extra downlink traffic. The P1 Pro is not itself a Wi-Fi gateway; plan a compatible network-connected device or supported client proxy only if your brief requires it.

Telemetry is a separate extension. The Telemetry module can share device battery and radio-load metrics and, on supported hardware, environmental sensor readings. Start with the device metrics already useful for your solar node. Add a sensor only when someone will use its readings and the extra reporting load fits your traffic budget. Verify sensor and connector support for the exact hardware before buying parts.

Extension decision

Write one of three decisions for each idea: needed now, test later, or no use case. For MQTT, state which endpoint requires Internet reach, which device would provide it, and what happens when the connection is down.

LESSON 06 / OPERATIONS

Leave a maintainable system.

A mesh is useful over time only when someone knows its settings, health, and recovery path.

Set a small inspection rhythm

For the solar site, watch battery level and voltage across days, plus channel utilization and airtime when available. Re-run a short two-way message test from your named stops after moving a node, changing a role, updating firmware, or changing a channel. Note the date, settings, and result. Review mounting, antenna connection, panel shade, and weather exposure at a cadence appropriate for the site.

Keep a configuration record for each exact hardware model: firmware version, region, preset, frequency slot, role, channel purpose, and update procedure. Store private keys separately in an appropriate secret store. Before any firmware update, read the exact device guide, record working settings, and plan a nearby recovery test. Seeed warns against the NRF-OTA update route for the P1 Pro; tracker instructions depend on their confirmed model labels.

Make the design reviewable

Your final plan should be understandable by someone who did not build the mesh. Show the required user route, current and candidate sites, measured versus predicted coverage, node roles, traffic budget, channel and location-sharing choices, power plan, optional extensions, maintenance owner, and failure fallback. Mark every claim as measured, predicted, or untested.

Capstone · mesh deployment plan
  • One-page service brief and success test
  • Site map with measured and predicted coverage distinguished
  • Configuration and traffic table for each node
  • Trust, location, power, and maintenance decisions
  • Recovery steps and an independent fallback

Print this page for the lesson checklist, or keep the plan in your own notes. Do not include secret keys.
